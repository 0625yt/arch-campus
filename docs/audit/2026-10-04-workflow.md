# 순차 실행 — 공유 요청 제한·장문 요약 비용, 2026-10-04

[워크플로](../EXECUTION-WORKFLOW.md)의 비용 보호를 이어서 구현했다. 운영 코드 배포, MFA 복구 코드, 작업 결과 저장의 멱등성, 푸시·캘린더·결제 전체를 완료했다는 의미는 아니다. 이전 인증·파일·문제 생성·작업 복구·PWA 증거는 [10월 3일 보고서](2026-10-03-workflow.md)를 따른다.

## 변경과 검증

- 운영 환경 변수 이름만 조회해 Upstash URL/토큰이 여전히 없는 것을 확인했다. 비밀 값은 출력하지 않았다. PR #4는 PR #3의 브랜치를 기반으로 하는 draft이며, 운영 병합·배포는 하지 않았다.
- Upstash가 없으면 기존 Supabase의 원자적 sliding window를 사용한다. AI 6회/분, 로그인 10회/5분, 업로드 30회/시간, 일반 요청 60회/분은 유지했다. 상품별 쿼터를 정한 것이 아니다.
- [0039](../../supabase/migrations/0039_shared_rate_limits.sql)는 HMAC 식별자·시각 배열·만료 시각을 저장한다. 사용자 ID·IP 원문은 저장하지 않는다. 서버 역할만 RPC/테이블에 접근하며 RLS를 켰다. 요청마다 만료 버킷을 최대 100개 정리하고 다른 요청의 잠금은 건너뛴다. 유휴 기간에는 즉시 지워지는 방식이 아니다.
- 같은 버킷의 요청은 행 잠금으로 직렬화하고 잠금을 얻은 뒤 시간을 읽는다. 저장소 장애·5초 응답 제한·잘못된 응답·운영 저장소 미설정은 503이며, 메모리로 우회하지 않는다. 메모리는 공유 저장소 없는 개발/테스트 환경에만 허용한다.
- 별도 테스트 스키마에서 정확한 마이그레이션을 실행했다. 독립 연결의 **동시 20개 중 6개만 승인**, 14개 차단·카운터/재시도 시각·사용자/종류 분리·만료·정리 상한·권한·원문 식별자 거절 등 **19개 통과**. 테스트 스키마 삭제 완료.
- API/DB 프로젝트 일치를 먼저 확인한 뒤 0039를 검증된 연결 DB와 마이그레이션 이력에 추가했다. 기존 사용자 행은 변경하지 않았다. 새 코드 배포 전에 필요한 구조를 준비한 것이며 운영 코드 반영과는 구분한다.
- 실제 임시 계정으로 HTTP 동시 20개 중 6개는 요청 형식 검사까지 도달하고, 14개는 AI 제한 429로 차단됐다. 공유 DB에 정확히 6개 hit, 다른 계정의 독립 한도, 응답 헤더, 생성/자료/작업 0개를 확인해 **로컬 API 7개 통과**. AI 호출은 0건이며 임시 계정·예약·버킷 삭제 완료.
- 읽기 전용 환경 검사 **28개 통과**. 추가 검사는 요청 제한 테이블의 서버 연결과 비로그인 접근 거절이다. 실제 모델 가용성 조회 옵션은 이번에 실행하지 않았다.

## 장문 요약 회귀

- 각 구간을 요약한 실제 호출의 사용량/비용에 합본 집계 값을 다시 더하던 버그를 수정했다. 합치는 과정은 AI 호출이 아니므로 별도 유료 생성으로 기록하지 않는다. 서로 다른 모델의 실제 비용도 각 호출의 단가대로 합산한다.
- 부분 요약이 매번 자료 캐시를 덮어쓰던 동작을 없애고 최종 합본만 갱신한다. 모든 구간이 실패하면 이전 캐시는 유지한다. 실패한 구간은 원래 번호를 보존하며 빠진 구간을 사용자에게 알린다.
- 형식/인용 검증에 실패해도 이미 청구된 알려진 사용량은 로그와 작업 합계에 포함한다. 공급자가 사용량 없이 오류를 던지면 실제 청구액을 알 수 없는 기존 한계는 남아 있다.
- 새 단위 회귀 **5개 통과**: 호출별 단일 집계·합본만 저장·모델별 단가·실패 비용과 누락 범위 안내·단일 호출·전체 실패 캐시 보존을 확인한다.
- 실제 가상 68K자 자료 평가: 두 구간 중 **1/2만 인용/형식 검증 통과**. 첫 실행은 모든 구간 성공을 기대한 검사에서 실패했다. 두 번째는 비용 집계·캐시 일치·실제 1/2 범위와 누락 안내 **3개를 검증**했다. 장문 요약 전체 품질이 통과한 것으로 세지 않는다.
- 두 번째 실행의 분류 포함 기록 기반 추정 비용 **$0.019674**. 첫 실행의 비용 합계는 실패 전에 캡처하지 못했고 임시 데이터는 정리됐으므로 두 실행 총비용은 알 수 없다. 공급자 청구서를 확인한 금액은 아니다. 두 실행 모두 임시 계정·자료·작업·생성 기록·버킷 삭제 완료.

## 검사 과정에서 수정한 판정

- DB 정리 검사 처음에는 1초 뒤 만료되는 롤링 윈도우를 활성 버킷으로 가정해 실패했다. 활성 사용자 버킷으로 검사 대상을 바꿔 19개 통과했다.
- HEAD 요청에는 오류 JSON이 없으므로 비로그인 테이블 거절의 SQL 코드가 비어 있었다. HTTP 401/403과 실제 오류를 확인하도록 읽기 전용 검사를 수정했다. 실제 GET과 PostgreSQL에서도 권한 거절을 확인했다.
- 요약 단위 fixture의 최소 블록/복습 항목 제약 누락을 실제 스키마에 맞췄다. 제품의 검증 기준은 완화하지 않았다. 장문 일부 실패에 대해서는 기존 부분 결과 제공 동작에 누락 범위와 비용을 정확히 연결했다.

## 실행 명령

```bash
npm run workflow:limits
npm run test:summary-chunks-live
npm run verify:env
npm run workflow:quality
```

`workflow:limits`는 단위 → 임시 스키마 DB → 실제 HTTP 검사 순서이며 서버가 필요하다. `test:summary-chunks-live`는 명시적으로 실행하는 실제 AI 평가이므로 비용이 발생한다. 부하 규모별 성능·실제 Vercel 인스턴스 수·스마트폰 푸시·결제는 이번 검증 범위가 아니다. 서비스 역할 키를 바꾸거나 Redis/Supabase 저장소를 전환하면 해당 짧은 윈도우의 카운터가 초기화될 수 있다.
