## 같은 자료의 실제 품질 비교

가상 통계·컴퓨터공학·일본어 노트를 같은 조건으로 비교했다. 원문·생성 결과의 모델 이름을 가린 별도 Gemini 3.8 감사 호출에 미리 작성한 핵심 기준을 제공했다. 인용·키워드에만 들어간 내용은 본문 보존으로 세지 않았다. 감사 판정 자체도 AI 결과이므로 발견한 결함을 직접 원문과 대조했다.

| 자료 | Haiku 요약 핵심 기준 | Flash-Lite 요약 핵심 기준 |
|---|---:|---:|
| 통계 | 7 / 8 | 8 / 8 |
| 컴퓨터공학 | 9 / 9 | 5 / 9 |
| 일본어 | 9 / 9 | 2 / 9 |
| 합계 | 25 / 26 | 15 / 26 |

감사 표본에서 원문과 반대되는 사실은 발견되지 않았다. Haiku도 통계의 ‘효과 크기 정의·실용적 중요성과의 구분’을 일부 생략했다. 실제 누락 결과를 회귀 자료로 삼아 요약 검수를 추가했고, 빠진 정의와 구분을 원문의 연속 인용과 함께 보충하는 것을 확인했다. 학생이 보지 않는 sourceQuote를 검수 입력의 요약에서 제거해, 인용만 있는 사실을 본문에 있는 것으로 착각하지 않도록 했다.

[비교 비용·시간](2026-10-15-vendor-comparison.json), [내용 감사 상세](2026-10-15-content-quality.json). 첫 비교 실행에서는 두 모델 모두 문제 18개를 통과했고, Haiku는 요약 생성 추정 비용 약 10%, 문제 생성+기존 검수 약 14%가 낮았다. Haiku 평균 시간은 요약 15.6초·문제 생성/검수 28.6초, Flash-Lite는 3.1초·7.2초였다. **이 수치는 새 요약 검수 비용을 포함하지 않는다.** 새 검수는 품질을 높이는 추가 비용이다. 한 번의 실행·작은 표본으로 전체 강의 품질이나 반복 성공률을 보장하지 않는다.

## 실제 오류 제보와 채점

DB `feedback` 17건을 읽고 남아 있는 문제와 풀이 결과를 대조했다. 삭제된 문제는 원래 문제를 복원해 판정할 수 없었다. 개인정보·사용자 식별자는 보고서에 저장하지 않았다.

- 결합도 종류를 묻는 문맥의 ‘제어’는 ‘제어 결합도’와 같은 답으로 인정한다. ‘개체 무결성’을 묻는데 상위 개념 ‘무결성’만 적는 것은 자동 정답으로 바꾸지 않는다.
- 한국어 띄어쓰기, 같은 값의 분수·소수, 호환 단위 환산을 처리한다. 접두어·다른 차원의 단위·일본어 촉음 오류·질문이 요구한 문자 체계는 구분한다.
- 지문·도표가 필요한 문제에 `passage`를 추가하고, 출제 검수와 풀이 화면 양쪽에서 사용한다. 필요한 제시문이 없거나 서버용 `&` 기호를 학생에게 강요하는 문제는 제외한다.
- 사용자가 원문·해설을 확인한 뒤 정답으로 인정하고 되돌릴 수 있다. 원래 자동 판정과 직접 인정 여부를 별도로 보관한다. 같은 풀이의 점수와 최신 오답 목록에 반영한다.
- 단답 동의어·부분 누락·어학 표기·서술형 반대 의미 등을 섞은 15건의 실제 모델 평가에서 Flash-Lite와 3.8 Flash는 기대 판정에 일치했다. Haiku는 잘못된 서술을 정답으로 승격하는 사례가 있어 보조 채점에 채택하지 않았다. 표기 제약은 서버에서도 고정한다.

## 긴 PDF와 시각 자료

기존에는 문서 정리 단계에서 60K자 이후가 잘렸고, 재사용을 위한 저장 시에도 200K자 제한이 있었다. 요약 합치기에서는 100블록을 넘으면 설명을 삭제했다. 이 조용한 절단을 제거했다.

- PDF 쪽수 표식을 보존하고 OCR의 각 부분에서 1부터 시작한 쪽수를 원본 절대 쪽수로 교정한다. 페이지 누락·잘림을 감지하면 더 작게 재시도하고, 실패한 쪽은 원문 텍스트 또는 추출 실패 표식을 남긴다.
- 최대 8쪽/50K자 단위로 나눠 전체를 처리한다. 3개 동시 실행으로 대기 시간을 줄인다. 구간 한 개라도 실패하면 이전 요약을 유지하며 완료본으로 저장하지 않는다. 처리 한도 초과 시 일부만 잘라 성공시키지 않는다.
- 표의 셀 개수·인용 위치를 검증한다. 비교표와 단계 도식은 구조화된 텍스트로 렌더링하며 생성 HTML/SVG를 실행하지 않는다. 모바일·태블릿·노트북에서 확인했다.
- PDF 저장은 React가 관리하는 본문을 떼어내는 방식에서 인쇄용 복사본으로 변경했다. 긴 인쇄 대화상자에서 임의 타이머로 복구하지 않는다. 표 머리글 반복과 행 나눔을 처리한다.
- 기존 PDF의 저장 본문에 쪽수 표식이 없거나 페이지가 부족하면, 다시 요약할 때 본인 소유 원본 파일을 재추출해 오래된 절단 본문을 복구한다.

100쪽 검증은 페이지별 고유 모듈 번호·점검 주기·임계값·방법 A/B 표본 수·센서 예외가 있는 **가상 텍스트 PDF**다. 전체 추출과 정리 후 100개 번호·고유 임계값, 표와 도식이 남는지 확인했다. 100쪽 OCR의 구간/절대 쪽수 처리는 별도 회귀 검사로 확인했다. 스캔·손글씨·복잡한 도형이 있는 모든 실제 100쪽 파일의 무누락을 보장하는 검사는 아니다. 최종 생성+검수 실행은 13개 구간, 약 131초, 추정 $0.2143으로 완료했다(분류·OCR 미포함, Google 할인 종료 후 단가). 100개 번호·임계값을 보존했고 21개 표·13개 도식을 생성했다. 화면의 범위 표시는 ‘입력 처리 범위’와 요약의 핵심 압축을 구분한다.

## 재현

```bash
# reportlab이 있는 Python 환경으로 가상 PDF 생성
python3 scripts/create-summary-eval-pdf.py
EVAL_REPORT_PATH=.tmp/vendor-quality-samples.json npm run test:model-upgrade-live
npm run test:grading-quality-live
npm run test:summary-100-live
# 모델 비교 rawText 표본을 쓴 내용 감사는 해당 경로를 지정
RUN_CONTENT_QUALITY_EVAL=1 node --env-file=.env.local node_modules/vitest/vitest.mjs run src/lib/eval/content-quality.integration.test.ts
npx playwright test e2e/summary-visual.spec.ts --workers=1
```

모델 호출 검사는 opt-in이며 비용이 발생한다. DB 저장은 모의 처리하고 고객 자료는 사용하지 않는다. 출력 PDF는 로컬 `output/pdf/summary-100-pages.pdf`에 생성한다. 배포는 이 보고서의 로컬 검증과 별개다.
