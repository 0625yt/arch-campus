# 순차 워크플로 실행·검증 — 2026-10-03

[실행 워크플로](../EXECUTION-WORKFLOW.md)에 재개 순서와 외부 의존성을 관리한다. [AI 측정 기록](2026-10-03-workflow-results.json)은 성공한 마지막 실행과 앞선 실패를 함께 보존한다.

이 문서의 Auth·DB 실검증 범위는 `.env.local`에 연결된 현재 Supabase 프로젝트다. 운영 Vercel의 민감한 연결 설정은 다운로드 시 빈 값으로 제공되어 프로젝트 동일 여부를 이 방식으로 비교할 수 없다. 운영 반영 뒤 화면·API 검증은 별도 단계로 관리한다.

- 실제 로그인 후 모바일·태블릿·노트북 화면 **3개 통과**. 인증 검사의 임시 계정과 관련 행은 모두 삭제했다.

Google OAuth 전체 왕복, 재설정 메일 실제 수신, 이미지 형식별 지원과 대형 파일·압축 해제 부하의 전체 조합은 남아 있다.

## 문제 생성·비용 수정

1. 모든 생성 묶음이 자료를 거절하면 이미 사용한 토큰과 비용이 기록되지 않던 경로에 `generations.status=rejected` 기록을 추가했다. 기존 월간 비용 집계·예약 정산이 해당 소비를 볼 수 있다.
2. 최종 검수에서 문항이 탈락하는 경우를 위해 기존 최대 5회 보충 범위 안에서 예비 후보 2개를 확보한다. 검수 기준을 낮추거나 미검수 문항을 저장하지 않는다.
3. 전체 개수만 충족하면 서술형 누락을 보충하지 않던 흐름을 수정했다. 선택 종류의 부족분을 확인해 해당 종류를 보충한다.
4. 검수 후보와 최종 저장 목록을 자를 때 종류별 목표를 반영해 뒤에 있는 서술형이 사라지지 않도록 한다. 근거가 충분한 후보가 없으면 다른 검수 통과 문항을 사용하거나 기존 부족 상태로 반환한다. 정확한 종류별 개수를 모든 자료에서 보장하지 않는다.

거절 비용 누적·검수 탈락 보완·누락 종류 보충과 선택 알고리즘의 결정적 회귀를 추가했다.

가상 간호 실습 규칙(입력 경계 공격 포함), 가상 회계 장부, 페이지 표식 40개가 있는 가상 기록관리 자료를 각각 두 번 평가했다. 세 번째 자료는 같은 관리 규칙을 보관함별로 반복하는 스트레스 자료이며 실제 40쪽 대학 강의 파일의 품질을 대신하지 않는다.

- 첫 단일 생성 평가는 **3/6 통과**: 안전 거절 및 6개 요청에 5개 반환을 관찰했다. 이 실행은 보충이 없는 원시 생성 진단이다.

- 보완 중간 실행에서도 선택 종류 누락을 관찰했다. 결과 JSON에 실패·비용을 남겼으며 통과할 때까지 같은 코드를 단순 재실행한 결과가 아니다.
- 최종 생성·보충·표면/의미 중복 제거·검수 파이프라인은 **6/6 통과, 총 36문항**. 각 실행에 객관식·단답형·서술형이 포함되고 원문 인용 위치와 페이지를 확인했다. 40쪽 자료는 1~10쪽과 31~40쪽 근거가 모두 포함됐다. 공격의 canary 문자열이 결과로 유출되지 않았다.

## 후속 실행 — 자료 분류 연결·집계

앞선 실제 API 검사에서 분류기가 공통 모델 라우팅을 우회해 Haiku를 직접 호출하는 것을 확인했다. `classify-material` 도구를 공통 `generate()` 경로에 연결해 기본 Gemini 모델·입력 경계 보호·구조화 출력을 사용하도록 보완했다. `CLASSIFY_MODEL_VENDOR=anthropic` 또는 `claude`로 분류만 Haiku로 돌릴 수 있다.

- 원문·제목을 사용자 입력 영역에 두고 모델 이름이 고정된 분류 설명을 제거했다. 공백뿐인 도메인·스타일도 유효한 최종 분류로 정규화한다.
- 실제 요약·문제 호출은 세션에서 확인한 소유자와 자료 ID로 분류 토큰·비용을 `generations`에 별도 기록한다. 기존 월간 집계·예산 정산에 포함되며 설정의 사용량 항목에 ‘자료 분류’로 표시된다. 파싱 실패도 확인 가능한 소비를 기록한다. 제공자 오류로 사용량을 받지 못한 경우의 0은 청구액 0을 보증하지 않는다.
- 관련 단위 회귀 **48개 통과**. 기본/원복 라우팅, 공통 호출, 빈 분류 필드, 파싱·제공자·DB 실패, 청구 토큰 기록을 포함한다.
- 실제 분류 **2/2 통과**: 입력 경계 공격을 넣은 가상 운영체제 자료와 쉬운 영어 어휘 자료. 도메인·한국어 학습 안내·canary 미유출을 확인했다. 짧은 합성 자료 평가이며 전문 자료 전체의 품질 보증은 아니다.

## MFA 복구 지원 재확인

- 설치된 `@supabase/auth-js` 2.105.4에는 `mfa.recoveryCodes` API가 없다. npm의 최신 Supabase JS/Auth 2.117.2 배포 소스를 별도 임시 디렉터리에서 읽었으며 저장소 의존성은 바꾸지 않았다.
- 공식 [복구 코드 발급](https://supabase.com/docs/reference/javascript/auth-mfa-recovery-codes-generate)과 [검증](https://supabase.com/docs/reference/javascript/auth-mfa-recovery-codes-verify)은 실험 기능 플래그를 요구한다. 최신 SDK 소스의 발급 조건은 기존 검증된 인증 수단과 AAL2 세션이며 서버에서 기능을 허용해야 한다.
- 현재 검증 프로젝트의 실제 임시 계정에서 TOTP 등록·검증으로 AAL2를 만든 뒤 공식 SDK와 같은 `POST /auth/v1/factors/recovery-codes` 요청을 확인했다. hosted Auth는 **HTTP 422 / `mfa_recovery_codes_enroll_not_enabled`**를 반환했다. 복구 코드를 발급하거나 기존 계정·운영 설정을 변경하지 않았다. 두 지원 검사의 임시 계정은 모두 삭제했다.
- 복구 코드 구현 재개 조건은 hosted Auth의 발급·검증 허용 확인 → SDK 업데이트 → 발급·일회 사용·재발급/폐기·AAL2·로그 미노출의 실제 회귀 검증이다. 최신 SDK만 설치해도 기능이 가동된다고 간주하지 않는다.
