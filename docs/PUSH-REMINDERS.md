# 일정 푸시 알림 — 2026-10-07

코드와 회귀 검사는 구현했다. **운영 DB의 0042 적용, 전송 키, 새 배포, 예약 활성화와 실제 기기 수신은 아직 완료하지 않았다.** 현재 설정이 없는 환경에서는 화면에 준비 상태를 표시하며 권한을 요청하지 않는다.

## 사용자 흐름

1. 설정의 **이 브라우저 알림 켜기**를 누른 뒤 브라우저 알림에 동의한다. 페이지 진입만으로 동의창을 띄우지 않는다.
2. 캘린더에서 일정을 추가하거나 수정하며 시작 시각·10/30/60분·1/3/7일 전 알림을 고른다. 기본값은 알림 없음이다.
3. 알림을 누르면 캘린더를 연다. 잠금 화면에는 과목명·일정 제목·메모를 보내지 않는다.
4. 일정의 알림을 없음으로 바꾸거나 설정에서 해당 브라우저 구독을 해제한다. 구독 해제는 서버 저장을 먼저 삭제한다.

종일 일정은 해당 날짜 **한국 시간 0시**를 시작으로 계산한다. 알림 0은 시작 시각이며 null은 알림 없음이다. 시간표처럼 날짜별로 저장된 수업 행도 지원하지만 `recurrence_rule` 문자열의 가상 반복 회차는 확장하지 않는다. FSRS 매일 복습 알림은 별도 후속이다.

## 운영 활성화 순서

1. [0042 마이그레이션](../supabase/migrations/0042_push_reminders.sql)을 기존 0041 이후 적용하고 `supabase_migrations.schema_migrations`에 0042 이력을 남긴다. 기존 마이그레이션 파일은 수정하지 않는다.
2. 한 번 생성한 VAPID 키 쌍을 안전하게 보관하고 같은 값을 로컬 검증과 Vercel 운영 환경에 등록한다. `web-push`의 키 생성 명령은 로컬에서만 실행하고 출력은 커밋하거나 공유하지 않는다. 서버 환경변수는 아래와 같다. 공개 키도 런타임 GET에서 제공하므로 `NEXT_PUBLIC_` 접두사는 필요 없다.

| 변수 | 용도 |
|---|---|
| `VAPID_PUBLIC_KEY` | 브라우저가 구독에 사용하는 공개 키 |
| `VAPID_PRIVATE_KEY` | 서버의 전송 서명 키 |
| `VAPID_SUBJECT` | 운영 연락처 `mailto:` 또는 HTTPS 주소 |
| `PUSH_WORKER_SECRET` | 기존 작업 복구 키와 별개의 무작위 키, 최소 32자 |

3. 코드를 배포하고 로그인한 설정 화면에서 구독을 연결한다. 비로그인 구독 API 401, 잘못된 예약 키 401, 올바른 키의 준비 GET 200을 확인한다. 일반 GET은 알림을 보내지 않는다.
4. `npm run push:enable`로 기존 pg_cron·pg_net과 Vault를 이용한 1분 예약을 켠다. 이 명령은 운영 주소·DB 프로젝트 일치·배포 준비·0042 이력을 먼저 확인하고 기존 예약 이름을 재사용한다. `npm run push:disable`는 이 알림 예약만 해제한다. 이번 작업에서는 두 명령을 실행하지 않았다.
5. 전용 시험 계정으로 미래 시각의 가상 일정 하나를 만들고 실제 기기에서 수신·탭·해제 후 미수신을 확인한다. iPhone·iPad에서는 홈 화면에 추가한 앱에서 검사한다. 사용한 계정과 일정은 정리한다.

## 저장·보안·실패 처리

- `push_subscriptions`는 소유자 조회/삭제 RLS와 MFA restrictive policy로 보호한다. 등록 RPC는 service-role 전용이며 세션에서 받은 owner만 사용한다. API GET은 본인 구독의 SHA-256 해시와 공개 키만 반환하고 endpoint·암호화 키는 반환하지 않는다.
- 브라우저별 endpoint는 전역 고유하다. 다른 계정의 endpoint를 덮어쓰지 않으며 계정 전환 후 새 구독을 발급한다. 한 계정의 동시 등록도 DB 잠금 안에서 최대 10개로 제한한다.
- 전송 URL은 Google·Mozilla·Apple·Windows의 HTTPS 푸시 서비스로 제한한다. 내부 주소·자격증명·다른 포트·유사 도메인은 거절한다.
- `push_reminder_deliveries`는 일반 사용자 접근을 허용하지 않는다. 확정한 일정·구독 소유자·알림 시각 버전으로 전송을 식별하고, 예약 호출당 최대 5개를 `skip locked`로 선점한다.
- 선점마다 새 토큰을 발급한다. 2분 이상 중단된 선점은 재개하고 이전 토큰의 완료 요청은 거절한다. 일시적 장애는 1분 뒤 재시도하며 최대 3회로 종료한다. 전송 시각 10분 이후에는 오래된 알림을 보내지 않는다. 전송 기록은 30일 뒤 정리한다.
- 전송 직전에 일정 편집·삭제·동의 해제를 재확인한다. 푸시 서비스의 404/410은 만료 구독을 삭제하고 429/5xx/네트워크 장애는 제한된 재시도로 처리한다.
- 제공자의 접수와 DB 완료 사이 서버가 종료되면 재전송될 수 있다. 공급자 topic과 알림 tag를 같게 유지해 겹치는 표시를 줄이지만 **정확히 한 번 수신을 보장하지 않는다**. 접수 성공도 기기의 실제 표시 성공을 뜻하지 않는다.
- 현재 용량은 예약 한 번당 5개다. 대량 일정·다기기 알림에서 대기 시간이 길어질 수 있으므로 사용량 증가 전에 처리량과 10분 만료를 부하 검증해야 한다.

## 검사

```sh
npm run test:push
npm run test:push-db
npm run test:push-browser
```

단위 40개, 실제 연결 DB의 **임시 스키마** 22개, 모의 브라우저 구독/HTTP를 이용한 세 화면 크기 검사 12개를 통과했다. DB 검사는 운영 테이블·사용자·예약을 수정하지 않고 임시 스키마를 삭제한다. MFA 함수는 임시 스키마에서 AAL을 읽는 대체 함수로 두고 실제 restrictive policy와 권한을 검사한다. 실제 Auth MFA는 별도 기존 인증 검사로 확인했다. 실제 푸시 제공자 전송과 실제 스마트폰 수신은 이번 검증 범위에 포함되지 않는다.

구현 기준은 저장소의 Next.js 16.3.8 PWA 가이드, [web-push 공식 문서](https://github.com/web-push-libs/web-push), [PushManager 구독 API](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)를 확인했다.
